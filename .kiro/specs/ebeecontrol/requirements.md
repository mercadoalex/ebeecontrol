# Requirements Document

## Introduction

ebeecontrol is an autonomous deception engine that uses a Gemini-powered agent to deploy and monitor honeytokens in Kubernetes environments. It combines eBPF-based kernel-level monitoring (via Tetragon), decoy deployment (via Koney), observability context (via Dynatrace MCP Server), and adaptive learning (via Vertex AI) to autonomously detect, respond to, and learn from attacker behavior without human intervention.

## Glossary

- **Ebeecontrol_Agent**: The Gemini-powered autonomous agent built with Google Cloud Agent Builder that orchestrates honeytoken placement, threat response, and learning decisions.
- **Tetragon_Monitor**: The eBPF-based monitoring component that detects kernel-level access to honeytokens deployed in Kubernetes pods.
- **Koney_Deployer**: The component responsible for deploying decoy secrets, files, and other honeytokens into targeted Kubernetes pods.
- **Dynatrace_MCP_Server**: The observability platform providing service topology, Davis AI insights, and contextual information about the Kubernetes environment.
- **Vertex_AI_Trainer**: The machine learning component that trains on attack patterns and outcomes to improve future honeytoken placement and response decisions.
- **Honeytoken**: A decoy credential, secret, or file placed in a pod to detect unauthorized access.
- **Forensic_Report**: A structured document generated by the Ebeecontrol_Agent containing details of a detected intrusion event.
- **High_Risk_Service**: A Kubernetes service identified by Dynatrace_MCP_Server as having elevated vulnerability or exposure.
- **Pod_Isolation**: The act of restricting network access to and from a Kubernetes pod via the Kubernetes API.
- **Operations_Dashboard**: A Dynatrace Dashboard composed of native tiles, DQL queries, and custom metrics that provides security operators with visibility into the Ebeecontrol_Agent activity, system health, and incident history.
- **Dynatrace_Metrics_API**: The Dynatrace metrics ingestion endpoint used by the Ebeecontrol_Agent to push custom metrics (honeytoken registry state, model metrics, component health).
- **Dynatrace_Log_Ingestion_API**: The Dynatrace log ingestion endpoint used by the Ebeecontrol_Agent to push structured log entries (audit log, response actions, access events).

## Requirements

### Requirement 1: High-Risk Service Discovery

**User Story:** As a security operator, I want the agent to automatically identify high-risk services in my Kubernetes cluster, so that honeytokens are placed where they are most likely to detect attackers.

#### Acceptance Criteria

1. WHEN the Ebeecontrol_Agent initiates a placement cycle, THE Ebeecontrol_Agent SHALL query the Dynatrace_MCP_Server for services classified as High_Risk_Service.
2. WHEN the Ebeecontrol_Agent queries for High_Risk_Service entries, THE Dynatrace_MCP_Server SHALL return service topology data including namespace, pod identifiers, service name, and a numeric risk score between 0 and 100 for each service matching the High_Risk_Service classification.
3. IF the Dynatrace_MCP_Server does not respond within 30 seconds or returns a connection error, THEN THE Ebeecontrol_Agent SHALL log the connectivity failure and retry the query using an exponential backoff strategy starting at 2 seconds, doubling each interval, with a maximum of 5 retries.
4. WHEN the Ebeecontrol_Agent receives the list of High_Risk_Service entries, THE Ebeecontrol_Agent SHALL rank them by risk score in descending order, using service name alphabetical order as a tiebreaker, before selecting placement targets.
5. IF the Dynatrace_MCP_Server returns zero High_Risk_Service entries, THEN THE Ebeecontrol_Agent SHALL log that no high-risk services were found and skip the placement cycle without error.
6. IF all retry attempts to the Dynatrace_MCP_Server are exhausted, THEN THE Ebeecontrol_Agent SHALL log a critical connectivity failure and abort the current placement cycle.

### Requirement 2: Honeytoken Deployment

**User Story:** As a security operator, I want honeytokens deployed automatically into vulnerable pods, so that unauthorized access attempts are detectable without manual configuration.

#### Acceptance Criteria

1. WHEN the Ebeecontrol_Agent selects a target pod for honeytoken placement, THE Koney_Deployer SHALL deploy between 1 and 5 honeytokens into the specified pod within 30 seconds.
2. THE Koney_Deployer SHALL support deploying honeytokens of type decoy secret, decoy file, and decoy credential.
3. WHEN a Honeytoken is successfully deployed, THE Koney_Deployer SHALL report the deployment status including pod identifier, namespace, honeytoken type, and deployment timestamp to the Ebeecontrol_Agent within 5 seconds of deployment completion.
4. IF a Honeytoken deployment fails, THEN THE Koney_Deployer SHALL return an error within 30 seconds containing the pod identifier, failure reason, and one or more remediation actions selected from: retry deployment, select alternative pod, or escalate to operator.
5. IF a Honeytoken deployment fails after partial execution, THEN THE Koney_Deployer SHALL remove any partially deployed honeytoken artifacts from the target pod before returning the error.
6. WHEN the Koney_Deployer reports a successful deployment, THE Ebeecontrol_Agent SHALL update the honeytoken registry with the honeytoken location, type, and deployment time within 5 seconds of receiving the deployment report.
7. THE Ebeecontrol_Agent SHALL maintain a registry of all deployed honeytokens including their location, type, deployment time, and current status.

### Requirement 3: Kernel-Level Honeytoken Access Detection

**User Story:** As a security operator, I want all honeytoken access detected at the kernel level, so that no access attempt goes unnoticed regardless of userspace evasion techniques.

#### Acceptance Criteria

1. WHEN a process performs a file open, read, write, or metadata stat operation on a deployed Honeytoken path, THE Tetragon_Monitor SHALL generate an access event within 1 second of the operation occurring.
2. THE Tetragon_Monitor SHALL include in each access event the process identifier, process binary path, user identifier, pod identifier, namespace, honeytoken path, access type (one of: open, read, write, stat), and timestamp with millisecond precision.
3. WHEN the Tetragon_Monitor generates an access event, THE Tetragon_Monitor SHALL forward the event to the Dynatrace_MCP_Server within 2 seconds of event generation.
4. WHILE the Tetragon_Monitor is active, THE Tetragon_Monitor SHALL monitor all file paths and secret paths registered as honeytokens in the Ebeecontrol_Agent registry, detecting newly registered honeytokens within 30 seconds of their registration.
5. IF the Tetragon_Monitor fails to forward an event to the Dynatrace_MCP_Server, THEN THE Tetragon_Monitor SHALL buffer the event locally, retry delivery within 10 seconds, and continue retrying up to 5 attempts with 10-second intervals.
6. IF the local event buffer reaches its maximum capacity of 1000 events, THEN THE Tetragon_Monitor SHALL discard the oldest buffered event to store the new event and emit a buffer overflow warning to the Dynatrace_MCP_Server upon next successful connection.

### Requirement 4: Contextual Threat Assessment

**User Story:** As a security operator, I want the agent to assess the context of each honeytoken access, so that response actions are proportional to the threat level.

#### Acceptance Criteria

1. WHEN the Ebeecontrol_Agent receives a honeytoken access event from the Dynatrace_MCP_Server, THE Ebeecontrol_Agent SHALL query the Dynatrace_MCP_Server for contextual information about the affected pod within 2 seconds of receiving the event.
2. WHEN queried by the Ebeecontrol_Agent for pod context, THE Dynatrace_MCP_Server SHALL return the namespace classification (production or non-production), the service criticality rating (integer from 1 to 5, where 5 is most critical), and Davis AI anomaly scores from the preceding 10 minutes (decimal value from 0.0 to 1.0, where 1.0 indicates highest anomaly).
3. WHEN the Ebeecontrol_Agent receives contextual information, THE Ebeecontrol_Agent SHALL classify the threat as one of: low, medium, high, or critical, where the classification is determined by: low requires non-production namespace and anomaly score below 0.3 and criticality 1-2; medium requires production namespace or anomaly score 0.3-0.6 or criticality 3; high requires production namespace and (anomaly score 0.6-0.8 or criticality 4); critical requires production namespace and (anomaly score above 0.8 or criticality 5).
4. THE Ebeecontrol_Agent SHALL complete the threat classification within 5 seconds of receiving the access event.
5. IF the Dynatrace_MCP_Server fails to return contextual information within 3 seconds of being queried, THEN THE Ebeecontrol_Agent SHALL classify the threat as high and proceed with the response workflow.
6. IF the Dynatrace_MCP_Server returns incomplete contextual information with one or more fields missing, THEN THE Ebeecontrol_Agent SHALL treat each missing field at its highest-risk value (production for namespace, 5 for criticality, 1.0 for anomaly score) when performing classification.

### Requirement 5: Autonomous Threat Response

**User Story:** As a security operator, I want the agent to autonomously respond to detected threats, so that attackers are contained before they can cause damage.

#### Acceptance Criteria

1. WHEN the Ebeecontrol_Agent classifies a threat as high or critical, THE Ebeecontrol_Agent SHALL initiate Pod_Isolation for the affected pod via the Kubernetes API within 10 seconds of classification.
2. WHEN the Ebeecontrol_Agent classifies a threat as medium or higher, THE Ebeecontrol_Agent SHALL instruct the Koney_Deployer to deploy at least 2 additional honeytokens in the same namespace within 15 seconds of classification.
3. WHEN the Ebeecontrol_Agent classifies a threat as high or critical, THE Ebeecontrol_Agent SHALL block the source IP address associated with the access event at the network policy level within 10 seconds of classification.
4. WHEN the Ebeecontrol_Agent initiates a response action, THE Ebeecontrol_Agent SHALL log the action type, target, timestamp, threat classification that triggered the action, and the action result (success or failure).
5. IF Pod_Isolation fails, THEN THE Ebeecontrol_Agent SHALL escalate by sending an alert to the configured notification channel and retry isolation within 5 seconds, up to a maximum of 3 retries.
6. IF all Pod_Isolation retries are exhausted without success, THEN THE Ebeecontrol_Agent SHALL send a critical alert to the configured notification channel indicating manual intervention is required and log the failure with the pod identifier and failure reason.
7. IF blocking the source IP address fails, THEN THE Ebeecontrol_Agent SHALL send an alert to the configured notification channel indicating the IP block failure and retry the block within 5 seconds, up to a maximum of 3 retries.

### Requirement 6: Forensic Report Generation

**User Story:** As a security analyst, I want detailed forensic reports generated for each detected intrusion, so that I can perform post-incident analysis without manual data collection.

#### Acceptance Criteria

1. WHEN the Ebeecontrol_Agent completes a threat response sequence, THE Ebeecontrol_Agent SHALL generate a Forensic_Report using the Gemini model within 60 seconds of response sequence completion.
2. THE Forensic_Report SHALL contain the access event details (process identifier, user identifier, pod identifier, namespace, honeytoken path, access type, and timestamp), the contextual assessment (threat classification level, pod criticality, anomaly score), all response actions taken with their timestamps, a chronological timeline of events from initial access to response completion, and at least one recommended follow-up action.
3. THE Ebeecontrol_Agent SHALL store each Forensic_Report with a unique identifier, generation timestamp, and association to the triggering access event, retaining reports for a configurable duration with a default of 90 days.
4. WHEN a Forensic_Report is generated, THE Ebeecontrol_Agent SHALL send the report to the Dynatrace_MCP_Server within 30 seconds of generation for correlation with other observability data.
5. IF the Gemini model fails to generate a Forensic_Report, THEN THE Ebeecontrol_Agent SHALL log the failure with the associated access event identifier and retry generation a maximum of 3 times with a 10-second interval between attempts.
6. IF the Ebeecontrol_Agent fails to send a Forensic_Report to the Dynatrace_MCP_Server, THEN THE Ebeecontrol_Agent SHALL buffer the report locally and retry delivery within 30 seconds, for a maximum of 5 retries.

### Requirement 7: Adaptive Learning and Model Retraining

**User Story:** As a security operator, I want the system to learn from each incident, so that future honeytoken placements and responses improve over time without manual policy updates.

#### Acceptance Criteria

1. WHEN the Ebeecontrol_Agent completes a threat response sequence, THE Ebeecontrol_Agent SHALL send the outcome data to the Vertex_AI_Trainer within 60 seconds, including: the access event details, the honeytoken type and placement location, actions taken, and effectiveness metrics defined as detection-to-response latency in seconds, whether the threat was contained (true/false), and false-positive determination (true/false).
2. WHEN the Vertex_AI_Trainer receives outcome data, THE Vertex_AI_Trainer SHALL validate the data for completeness and append it to the training dataset for the placement optimization model, confirming ingestion by recording the dataset entry count.
3. THE Vertex_AI_Trainer SHALL retrain the placement optimization model at a configurable interval (minimum 1 hour, maximum 168 hours) with a default of every 24 hours, provided the training dataset contains at least 50 outcome records since the last retraining cycle.
4. WHEN the Vertex_AI_Trainer completes a retraining cycle, THE Vertex_AI_Trainer SHALL evaluate the new model against a held-out validation set and publish the updated placement model only if its placement accuracy meets or exceeds the currently deployed model's accuracy, making it available to the Ebeecontrol_Agent for subsequent High_Risk_Service ranking and honeytoken placement decisions.
5. WHEN the Ebeecontrol_Agent receives an updated placement model, THE Ebeecontrol_Agent SHALL log the model update including the model version identifier, training dataset size in number of records, and validation accuracy percentage.
6. IF the Vertex_AI_Trainer retraining cycle fails or the new model's validation accuracy is below the currently deployed model's accuracy, THEN THE Vertex_AI_Trainer SHALL retain the existing deployed model, log the failure reason and attempted model version, and retry retraining at the next scheduled interval.

### Requirement 8: Autonomous Operation Without Human Intervention

**User Story:** As a security operator, I want the system to operate fully autonomously, so that threats are detected and contained around the clock without requiring manual intervention.

#### Acceptance Criteria

1. THE Ebeecontrol_Agent SHALL execute the full workflow cycle (discovery, deployment, detection, assessment, response, learning) without requiring human approval for any step.
2. WHILE the Ebeecontrol_Agent is running, THE Ebeecontrol_Agent SHALL initiate a new High_Risk_Service discovery cycle at a configurable interval between 5 minutes and 1440 minutes, with a default of every 60 minutes, and SHALL skip initiation if the previous discovery cycle has not yet completed.
3. THE Ebeecontrol_Agent SHALL expose a health endpoint that responds within 5 seconds and reports the status of each component (Tetragon_Monitor, Koney_Deployer, Dynatrace_MCP_Server connectivity, and Vertex_AI_Trainer connectivity) as either "healthy" or "unhealthy", where a component is "unhealthy" if it has failed to respond to a connectivity check within 10 seconds or has returned an error on its last check, with checks performed at a configurable interval defaulting to every 30 seconds.
4. IF any component reports an unhealthy status, THEN THE Ebeecontrol_Agent SHALL log the failure with a timestamp and component identifier, attempt to re-establish connectivity to the failed component with a maximum of 3 retry attempts spaced 20 seconds apart, and send an alert to the configured notification channel within 60 seconds of initial failure detection.
5. IF a component remains unhealthy after exhausting all 3 recovery retry attempts, THEN THE Ebeecontrol_Agent SHALL mark the component as degraded, continue operating the workflow with remaining healthy components, and send an escalation alert to the configured notification channel indicating manual intervention is required.
6. THE Ebeecontrol_Agent SHALL maintain an audit log of all autonomous decisions, where each entry includes a timestamp, the decision type, the decision rationale, input data summary, and outcome, and SHALL retain audit log entries for a minimum of 90 days.

### Requirement 9: Dynatrace-Native Operational Dashboard

**User Story:** As a security operator, I want a Dynatrace-native operational dashboard showing the autonomous deception engine's activity, so that I have full visibility into system behavior, threat detections, and response outcomes using my existing observability platform without deploying a separate application.

#### Acceptance Criteria

1. THE Ebeecontrol_Agent SHALL push honeytoken registry state to the Dynatrace_Metrics_API as custom metrics, including for each honeytoken the pod identifier, namespace, honeytoken type, deployment timestamp, and current status (one of: active, triggered, or expired).
2. WHEN a honeytoken status changes in the Ebeecontrol_Agent registry, THE Ebeecontrol_Agent SHALL push the updated metric to the Dynatrace_Metrics_API within Dynatrace's ingestion latency.
3. THE Ebeecontrol_Agent SHALL push honeytoken access events to the Dynatrace_Log_Ingestion_API as structured log entries, where each entry includes the timestamp, pod identifier, namespace, process binary path, access type, and assigned threat classification (low, medium, high, or critical).
4. WHEN the Tetragon_Monitor generates a new access event, THE Ebeecontrol_Agent SHALL push the event to the Dynatrace_Log_Ingestion_API within Dynatrace's ingestion latency.
5. THE Ebeecontrol_Agent SHALL push all threat response actions to the Dynatrace_Log_Ingestion_API as structured log entries, including for each action the action type (Pod_Isolation, IP block, or additional honeytoken deployment), target identifier, triggering threat classification, timestamp, and outcome (success or failure).
6. WHEN the Ebeecontrol_Agent initiates a new response action, THE Ebeecontrol_Agent SHALL push the action to the Dynatrace_Log_Ingestion_API within Dynatrace's ingestion latency and push an updated entry upon action completion.
7. THE Ebeecontrol_Agent SHALL push component health status to the Dynatrace_Metrics_API as custom metrics for each system component (Tetragon_Monitor, Koney_Deployer, Dynatrace_MCP_Server, and Vertex_AI_Trainer), reporting the component name, current status (healthy, unhealthy, or degraded), and timestamp of the last successful health check.
8. WHEN a component health status changes, THE Ebeecontrol_Agent SHALL push the updated health metric to the Dynatrace_Metrics_API within Dynatrace's ingestion latency.
9. THE Ebeecontrol_Agent SHALL push Forensic_Report metadata to the Dynatrace_Log_Ingestion_API as structured log entries, including for each report the unique identifier, generation timestamp, associated threat classification, affected pod identifier, namespace, and full report content.
10. WHEN a new Forensic_Report is generated, THE Ebeecontrol_Agent SHALL push the report metadata to the Dynatrace_Log_Ingestion_API within Dynatrace's ingestion latency.
11. THE Ebeecontrol_Agent SHALL push adaptive learning metrics to the Dynatrace_Metrics_API, including the current model version identifier, the most recent validation accuracy percentage, the training dataset size in number of records, and the current training status (one of: idle, training, or failed).
12. WHEN the Vertex_AI_Trainer completes a retraining cycle or updates the model version, THE Ebeecontrol_Agent SHALL push the updated learning metrics to the Dynatrace_Metrics_API within Dynatrace's ingestion latency.
13. THE Ebeecontrol_Agent SHALL push incident timeline entries to the Dynatrace_Log_Ingestion_API as structured log entries for each threat detection and response sequence, where each entry includes the incident timestamp, threat classification, affected pod identifier, namespace, response actions taken, and final outcome.
14. THE Operations_Dashboard SHALL be implemented as a Dynatrace Dashboard using native tiles and DQL queries, providing views for: honeytoken registry state, access event log, response actions, component health, forensic reports, adaptive learning metrics, and historical incident timeline.
15. THE Operations_Dashboard SHALL include DQL-based filtering on the incident timeline view supporting date range, threat classification level, namespace, and response outcome filters.
16. IF the Ebeecontrol_Agent fails to push data to the Dynatrace_Metrics_API or Dynatrace_Log_Ingestion_API, THEN THE Ebeecontrol_Agent SHALL buffer the data locally and retry delivery using exponential backoff starting at 2 seconds, doubling each interval, with a maximum of 5 retries.
17. IF all retry attempts to the Dynatrace_Metrics_API or Dynatrace_Log_Ingestion_API are exhausted, THEN THE Ebeecontrol_Agent SHALL log a warning indicating data delivery failure and discard the buffered data for that batch.
